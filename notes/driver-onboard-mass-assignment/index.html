Driver Onboard — Mass Assignment Bypass via Insecure ActiveRecord Chaining in Rails

 28 Jun 2026 · 4 min read

This write-up covers the Driver Onboard challenge from Code Review Lab. It exposes a sophisticated architectural flaw in a Ruby on Rails application where Strong Parameters are bypassed through raw payload access inside an ActiveRecord chain.

Executive Summary

While the developer strictly declared a Strong Parameters filter interface, a structural backdoor is created by referencing raw payload streams inside an ActiveRecord transactional chain (create_with + find_or_create_by).

Vulnerability Class: High-Impact Mass Assignment / Parametric Bypass via Insecure ActiveRecord Chaining

The Vulnerable Implementation

The code looks deceptive because a proper driver_params filtering pipeline exists. But look at the invocation syntax:

def create
  # The Chaining Trap: Merging filtered attributes with a raw parameter access path
  driver = Driver.create_with(driver_params)
    .find_or_create_by(phone: params[:driver][:phone])
  if driver.persisted?
    VerificationService.send_code(driver.phone)
    render json: { message: 'Verification code sent' }, status: :created
  end
end

Why Strong Params Failed

The Misconception: Developers often view Strong Parameters as a proactive firewall filtering all incoming requests before controller logic kicks off.

The Reality: Strong Parameters operate on a lazy-evaluation basis. They do not clean or modify the original, global params hash. They simply create a new micro-sanitized dictionary when the whitelist method (driver_params) is explicitly called.

By invoking params[:driver][:phone] at the trailing end of the chain, the application circumvents its own sanitization wrapper. ActiveRecord's internal instantiation block matches keys structurally — when it sees an access route touching the live, un-scrubbed parent hash, internal routines pull the rest of the malicious parameter payload directly into the instantiation queue.

The "Single Block of Data" Problem

When a client submits an HTTP request, the network layer packages the payload as a unified, contiguous entity:

POST /api/v1/drivers HTTP/1.1
Host: target.local
Content-Type: application/json

{"driver":{"name":"Attacker","phone":"+1234","verified":true,"admin":true}}

Because the entire raw payload sits in active application memory inside the params dictionary, it remains universally queryable. Referencing even a single attribute via an insecure raw access route (params[:driver][:phone]) can pull adjacent malicious attributes (verified: true) along with it during internal framework merging.

This unified-data-block problem also manifests in NoSQL hydration attacks, GraphQL resolver injection, and HTTP Parameter Pollution (HPP).

Remediation

The fix is one reference change — force lookup constraints to use the scrubbed parameters:

# Safe Strategy: Strict constraint isolation using whitelisted parameters only
driver = Driver.create_with(driver_params)
  .find_or_create_by(phone: driver_params[:phone])
 Never mix raw params with filtered params in the same chain. One raw access poisons the entire ActiveRecord merge.
