GridAdmin JWT — Algorithm Confusion and How HS256 Hijacks RS256 Verification

 28 Jun 2026 · 4 min read

This case study breaks down the GridAdmin JWT challenge from Code Review Lab. It exposes a classic JWT Algorithm Confusion vulnerability — where a misconfigured verification allow-list lets an attacker forge admin tokens using nothing but a public key.

The Vulnerability: JWT Algorithm Confusion

The provided code contains a critical authentication bypass due to JWT Algorithm Confusion. The application exposes an allow-list configured to accept both asymmetric (RS256) and symmetric (HS256) algorithms within the same verification execution path:

VERIFY_ALGS = ["RS256", "HS256"]

How It Fails

1. Asymmetric vs. Symmetric

The system retrieves an RSA public key via public_key_pem() to verify RS256 tokens minted by the corporate SSO. Public keys are inherently public and non-secret by design.

2. The Key Confusion

When an attacker crafts a malicious token with the header {"alg": "HS256"}, the underlying jwt.decode library switches to symmetric verification mode.

3. The Exploit Mechanism

Because HS256 is in the allowed list, the library treats the provided key — which contains the public RSA key bytes — as a raw HMAC symmetric shared secret. An attacker can sign a forged token (e.g., specifying {"role": "admin"}) using the freely available public key bytes as the HMAC secret, completely bypassing authentication.

TL;DR: When both RS256 and HS256 are allowed, an attacker feeds the public RSA key as the HMAC secret. The public key becomes the signing key. Game over.

Flaw Mechanism — Step by Step

  1. Context Mismatch: The code pulls a public key via public_key_pem() to verify legitimate tokens signed by an asymmetric corporate SSO (RS256). Public keys are entirely non-secret by design.
  2. Attacker Control: By sending a token with a modified header reading {"alg": "HS256"}, an attacker forces the decoding library to shift to a symmetric validation context.
  3. Key Abuse: Because HS256 is explicitly permitted in VERIFY_ALGS, the decoding library treats the provided key parameter (the public RSA key string) as a raw symmetric HMAC shared secret. An attacker signs a forged payload — granting administrative roles — using the publicly visible key bytes as the HMAC secret, bypassing validation seamlessly.

Remediation

To mitigate algorithm confusion, restrict allowed validation criteria strictly to the expected cryptographic architecture. Enforce strict separation between algorithms and the keys associated with them, or drop support for legacy symmetric tokens entirely if they are no longer required.

Secure Implementation

def verify_token_secure(token: str) -> dict:
    key = public_key_pem()
    try:
        claims = jwt.decode(
            token,
            key=key,
            algorithms=["RS256"],  # Explicitly remove HS256
            audience=EXPECTED_AUDIENCE,
            issuer=EXPECTED_ISSUER,
        )
    except jwt.PyJWTError as exc:
        raise TokenError(str(exc))

    if "role" not in claims:
        raise TokenError("missing role claim")
    return claims
 The fix is one line: Change ["RS256", "HS256"] to ["RS256"]. Never let a public key double as a symmetric secret.

Key Takeaways

  • Algorithm allow-lists are security boundaries. Every algorithm you add expands the attack surface.
  • Public keys are not secrets. If your verification logic treats them as HMAC secrets under any code path, you have a vulnerability.
  • Prefer explicit over permissive. algorithms=["RS256"] is safer than ["RS256", "HS256"] every time.
