Deconstructing the Token Burn Bug

 26 Jun 2026 · 5 min read

Executive Summary

In smart contract security, a single typo can separate a secure protocol from total economic collapse. The Token Burn Bug from Code Reviewlab demonstrates one of the most devastating yet deceptively simple logic flaws in Solidity: parameter flipping within authorization mappings. The failure is not complex math or an EVM edge-case — it's a human-error flaw where variables were transposed during a critical access control check.

Core Concept: Owner vs. Spender

Standard ERC-20 tokens track delegated spending limits through a nested mapping: 

mapping(address => mapping(address => uint256)) private _allowances;

function allowance(address owner, address spender) public view returns (uint256)
  • 1st Parameter (owner): The Authorizer — holds the tokens and delegates spending privileges
  • 2nd Parameter (spender): The Delegate — authorized to withdraw up to the delegated limit

The Flawed Code

function burnFrom(address from, uint256 amount) external returns (bool) {
    address spender = msg.sender;
    // ❌ VULNERABILITY: Parameter positions are reversed!
    uint256 currentAllowance = allowance(spender, from);
    require(currentAllowance >= amount, "Burn amount exceeds allowance");
    _approve(from, spender, currentAllowance - amount);
    _burn(from, amount); // 💥 Destroys tokens from the targeted address
    return true;
}

The critical line is allowance(spender, from). Because the ERC-20 standard treats the first argument as the owner, the EVM interprets spender (the attacker) as the token owner and from (the victim) as the delegate.

Instead of asking "Did the victim authorize the attacker to burn their tokens?", the logic asks "Did the attacker authorize the victim to spend the attacker's tokens?" — a question the attacker controls completely.

Step-by-Step Attack Vector

1. Manipulating the Ledger State

Eve (attacker) targets Alice (victim), who holds a high GG token balance. Eve calls the standard approve function: 

token.approve(Alice, 1000000);

This records _allowances[Eve][Alice] = 1000000. Eve has injected a massive allowance ceiling into the ledger — on her own terms.

2. Bypassing the Authorization Gate

Eve calls burnFrom(Alice, 500). Within this execution frame, spender resolves to Eve and from resolves to Alice: 

uint256 currentAllowance = allowance(Eve, Alice); // Resolves to 1,000,000
require(1000000 >= 500); // 🟢 Satisfied — Eve authorized this!

3. Targeted Asset Eradication

The internal _burn function bypasses allowance checks entirely, altering the balance mapping directly. 500 real tokens are permanently destroyed from Alice's balance — while Eve's balance remains untouched. The allowance drops to 999,500, leaving Eve ample headroom to repeat until Alice's balance hits zero.

Ledger State During Exploit

Allowance Ledger (_allowances[Eve][Alice]): 1,000,000 → 999,500. Permission ceiling drops; no assets altered.

Alice's Wallet (_balances[Alice]): 5,000 GG → 4,500 GG. 500 legitimate tokens permanently destroyed.

Eve's Wallet (_balances[Eve]): 0 GG → 0 GG. Attacker remains entirely unaffected.

Remediation

The fix is a one-line parameter swap — aligning with the ERC-20 standard's structural ordering: 

// FIXED: "from" is the asset owner; "spender" is the caller.
uint256 currentAllowance = allowance(from, spender);

Now the check correctly asks: "Did Alice (from) authorize Eve (spender)?" — which Eve cannot fabricate.

Security Takeaway

The Token Burn Bug illustrates that code readability and strict adherence to architectural standards are vital to smart contract safety. When extending or overriding standard token functions, ensure the true Authorizer occupies the primary parameter position. A single transposition in an authorization mapping is not a minor style issue — it is an economic vulnerability with direct financial consequences.
