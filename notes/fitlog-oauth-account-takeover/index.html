FitLog OAuth Login — How Exported Activities, Custom URL Schemes, and Missing PKCE Enable Full Account Takeover

 25 Jun 2026 · 7 min read

This case study breaks down the FitLog OAuth Login challenge from Code Review Lab. It highlights how a security auditor connects the dots between a public component (exported="true") and an insecure data pathway to uncover a full account takeover.

Part 1: The Code Review Trail — How It's Tracked Down

When auditing a mobile app for security vulnerabilities, looking at individual lines of code out of context rarely tells the full story. Instead, attackers and code reviewers follow a trail of data. Here is exactly how this bug is tracked down in the FitLog codebase:

Step 1: The Initial Entry Point — AndroidManifest.xml

The review begins in the manifest. You notice android:exported="true" on the OAuthCallbackActivity.

Thought process: Why is this activity exposed to the public?

Finding: It handles an intent-filter designed to catch browser traffic:

<data android:scheme="fitlog" android:host="oauth-callback" />

This confirms that the app uses a Custom URL Scheme (fitlog://) to receive data back from the web browser during login.

Step 2: Tracing the Logic — OAuthCallbackActivity.kt

The reviewer immediately jumps to the code behind that activity to see how it handles incoming data. They check the onCreate or onNewIntent methods.

Finding: The activity reads the intent, extracts an authorization query parameter (e.g., ?code=XYZ123), and prepares to use it.

Step 3: Checking the Handshake — OAuthManager.kt

Next, the reviewer investigates how that code is traded for a real login token. They look at OAuthManager.kt.

The trap: The reviewer looks for PKCE (Proof Key for Code Exchange). PKCE requires two unique things: a dynamic code_challenge sent at the start of login, and a secret code_verifier sent at the end.

Finding: There is no PKCE logic in OAuthManager.kt. The token exchange relies entirely on a static, hardcoded client_id and client_secret bundled inside the app's code.

Part 2: The Vulnerability Explained from the Start

Now that the components are mapped out, the vulnerability becomes clear. The flaw isn't just one single setting — it is a chain reaction of three weak security choices:

exported="true" + Custom URL Scheme + No PKCE = Full Account Takeover

1. The Core Flaw: Custom Schemes Are Unregulated

On a desktop computer, a domain name like google.com can only belong to one owner. On Android, custom URL schemes have no ownership verification. Any malicious app downloaded onto a victim's phone can put this exact line in its own manifest:

<data android:scheme="fitlog" android:host="oauth-callback" />

Android does not block this. It happily lets multiple apps register for the exact same custom scheme.

2. How the Attack Plays Out

Step What Happens
1. The victim logs in The user opens the legitimate FitLog app and taps "Log in with OAuth". The phone opens Chrome to let them authenticate.
2. The server redirects The user logs in successfully. The OAuth server issues an authorization code and sends Chrome to: fitlog://oauth-callback?code=SECRET_CODE_HERE
3. The interception Chrome drops that link back into the Android OS to route it. Because the malicious app registered that exact same scheme, Android gets confused — it may quietly deliver that SECRET_CODE straight to the attacker's app instead of FitLog.
4. The compromise Because the developers left out PKCE, the malicious app doesn't need to prove it started the login. The attacker extracts the hardcoded client_secret from the FitLog APK, bundles it with the stolen code, sends it to the OAuth token endpoint, and logs into the victim's account.

Part 3: Why exported="true" Is the Necessary Evil That Opened the Gate

Your instinct to flag android:exported="true" was entirely correct. It is the catalyst for the bug, but it's important to understand why it was configured that way.

Why the developer did it: For OAuth to work on mobile apps, the login happens inside an external browser (like Chrome or Firefox). When login finishes, the browser needs permission to wake the app back up and deliver the code. Setting exported="true" gives external apps (like Chrome) permission to launch OAuthCallbackActivity. If it were false, the browser would trigger a security crash, and users could never log in.

Why it creates a vulnerability here: Setting exported="true" opens an authentication gateway to the entire phone. If you open a door to the public, you must verify who enters. Because the developer paired an exported activity with an unverified custom scheme (fitlog://), they allowed rogue applications to intercept the traffic before it could ever hit the door.

The Fix

To secure the application, the custom scheme must be swapped out for an Android App Link utilizing android:autoVerify="true" over an HTTPS domain (e.g., https://fitlog.com/callback). This forces Android to check a signature file on the server, cryptographically locking the link handler to the official FitLog app configuration.

Key takeaway: exported="true" is often necessary for OAuth flows — but it must be paired with verified link handling (App Links, not custom schemes) and PKCE to prevent code interception. Without both, you've built a door that anyone can walk through.
