Charity Tokens — ERC677 Callback Reentrancy and the Checks-Effects-Interactions Violation

 28 Jun 2026 · 5 min read

This case study breaks down the Charity Tokens challenge from Code Review Lab. It exposes a critical ERC677 Callback Reentrancy vulnerability — a violation of the Checks-Effects-Interactions paradigm that lets a malicious beneficiary drain the entire token vault.

Executive Summary

The DonationToken.sol smart contract implements a decentralized charity framework utilizing the ERC677 token standard. The platform uses an automated callback mechanic via the transferAndCall interface designed to seamlessly notify beneficiary contracts immediately upon processing incoming donations.

An audit of the implementation revealed a critical Reentrancy Vulnerability caused by a violation of the Checks-Effects-Interactions design paradigm. A malicious beneficiary architecture can intercept execution control during the external callback phase and execute recursive calls back into the asset depletion logic, fully draining the underlying token vault before the parent transaction frames resolve.

The Vulnerable Code

The following code segment contains the core functional sequence within the DonationToken ledger. Note the operational distribution order regarding state adjustments and external invocations:

function transferAndCall(
    address to,
    uint256 amount,
    bytes calldata data
) external returns (bool) {
    // 1. CHECK: Verify if the donor holds a sufficient balance
    require(balances[msg.sender] >= amount, "Insufficient balance");

    // 2. EFFECT: Modify state parameters on the internal ledger
    balances[msg.sender] -= amount;
    balances[to] += amount;

    // ⚠️ 3. INTERACTION (THE GLITCH): External call to an untrusted contract
    if (isContract(to)) {
        IERC677Receiver(to).onTokenTransfer(msg.sender, amount, data);
    }

    // 4. FINALIZE: Transaction frame attempts to complete execution cleanly
    return true;
}
 The flaw: State is updated BEFORE the external call. Once control is handed to an untrusted contract via onTokenTransfer, the attacker re-enters before the function can finalize.

Chronological Exploitation Flow

Layer 1: The Ingress Entry (Execution Frame 1)

  1. An attacker calls transferAndCall targeting their deployed MaliciousBeneficiary contract. The EVM allocates Execution Frame 1.
  2. The require check validates balances — it clears.
  3. Internal accounting deducts from the attacker and credits the beneficiary contract.
  4. Execution reaches IERC677Receiver(to).onTokenTransfer(...).
  5. Critical freeze: DonationToken's context pauses at this line. It cannot reach the return true statement. Control is handed to the receiver.

Layer 2: The Re-entrant Ambush (Execution Frame 2)

  1. Inside the attacker's contract, onTokenTransfer immediately calls DonationToken.transferAndCall() a second time.
  2. No execution gates or status checks block entry. The EVM builds Execution Frame 2 on top of the paused Frame 1.
  3. Validation illusion: The require check executes again. Since Frame 1's state changes are already committed, the attacker's contract has already been credited — the nested balance check passes.
  4. The contract processes state updates again, reaches the callback line, and freezes Frame 2 — handing control back to the attacker to spawn Frame 3.
The stack consequence: Frame 1 → Frame 2 → Frame 3 … indefinitely. The contract leaks tokens at every interaction boundary without ever reaching the closing block, until the pool is completely drained.

Remediation

To fully secure the asset routing framework, the platform must enforce defensive state boundaries using OpenZeppelin's industry-standard ReentrancyGuard component. This integrates an explicit mutex variable directly into the function invocation wrapper.

How the Mutex Guard Aborts the Loop

  1. Initial ingress: The nonReentrant modifier reads the security flag. Finding it UNLOCKED, it sets it to LOCKED before letting execution pass inside the main code block.
  2. Intercept check: When the attacker attempts a nested re-entry call, the modifier checks the flag a second time.
  3. Defensive reversion: Because the flag reads as LOCKED, the system immediately throws an exception. The nested frame crashes, resetting all pending modifications and preserving token liquidity.

Secure Implementation

import "@openzeppelin/contracts/security/ReentrancyGuard.sol";

contract SecureDonationToken is IERC677, ReentrancyGuard {
    mapping(address => uint256) public balances;

    event Transfer(address indexed from, address indexed to, uint256 value);

    function isContract(address account) internal view returns (bool) {
        return account.code.length > 0;
    }

    function transferAndCall(
        address to,
        uint256 amount,
        bytes calldata data
    ) external override nonReentrant returns (bool) {
        require(balances[msg.sender] >= amount, "Insufficient balance");
        balances[msg.sender] -= amount;
        balances[to] += amount;

        emit Transfer(msg.sender, to, amount);

        if (isContract(to)) {
            IERC677Receiver(to).onTokenTransfer(msg.sender, amount, data);
        }

        return true;
    }
}
 The fix is one modifier: Add nonReentrant to any function that makes external calls after state changes. One word prevents infinite recursion.

Key Takeaways

  • Checks-Effects-Interactions is law. State changes must happen last, or be guarded by a mutex.
  • ERC677's callback is a double-edged sword. The transferAndCall convenience creates a reentrancy surface every time it's used.
  • ReentrancyGuard is not optional. For any contract that makes external calls, nonReentrant should be the default, not an afterthought.
